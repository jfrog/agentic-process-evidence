# Feature branch development - Implementation

Two elements. Protocol needs both.

1. **Agent runtime tool** — telemetry capture, aggregate on commit, signed **agent-process-evidence** push
2. **Server** — persist (audit + troubleshooting), alignment checks, deployment gates time evaluations (policy-as-code)

Runtime tool produces. Server keeps and enforces. 

What the **agent-process-evidence** is *for*:

- **Agent identity** — harness, agent, model (requested vs resolved)
- **Provenance** — process bound to the git commit
- **Execution traceability** — points to the session timelines (tools, prompts, MCP) that affected the subject commit
- **Integrity & non-repudiation** — signed in-toto / DSSE, not editable after the fact
- **Policy-as-code** — gates evaluate the evidence before anything moves

---

## 1. Agent runtime tool

Sits next to the coding agent. Active on every session you intend to govern: chat, interactive_run, subagents, etc

### Telemetry capture

As the agent writes code or runs tests, the runtime tool logs operational context into **agentic-session-log**s buffer. Harness hooks are one way to capture that timeline.

The telemetry must also provide information that will allow to bind the session log to the entity space, in this case we need to attach to every session the base commits it worked on.

Each log carries `sessionId`, `provider` (harness / agent / models), and `parentSessionId` when it is a subagent. 

Example: `[objects_examples/agentic-session-log.json](./objects_examples/agentic-session-log.json)`.

### Aggregating on commit

For this use case we decided that the **Commit** is the process end.

On the commit event the runtime tool:

- Finds every session log that affected this commit — including subagents
- Stamps `affectedEntities.gitCommit` on those logs, using the base commit logged on the object
- One `traceId` for the process (could be ticket id for example)
- Unions `providers` and `tools` across sessions
- `startTimestamp` = first session start
- `endTimestamp` = commit time

Don't emit one process evidence per session. Sessions are not the process.

### Evidence push

Upload the session logs to persistent storage (`uri` + `sha256`).

Then craft **agentic dev process evidence**, sign it (in-toto + DSSE), and push to the SDLC management platform. Example: `[objects_examples/agentic-dev-process-evidence.json](./objects_examples/agentic-dev-process-evidence.json)`.

That is the handoff. After this the logs and the signed evidence live on the server.

---

## 2. Server

Receives the push. Keep it, check it, evaluate it at later choke points.

### Persistence — audit and troubleshooting

Session logs and evidence stay as long as the release is relevant, For a minimal time of least **6 months** (EU AI Act Art. 19).

Store them searchable. Minimum keys:

- `commit` / subject
- `sessionId` (and `parentSessionId`)
- `agent` / harness / models
- `tools`

Binding evidence and logs to standard SDLC entities (commit → package → release) is what makes post-release audit work — same idea as an SBOM.

If a tool or MCP is later identified as malicious: search the session logs that used it, walk those logs to the commits and the software releases that shipped them.

Process evidence on the commit is the index. Session logs are the drill-down.

### Alignment check

The server MAY emit **alignment evidence** per session log (`ALIGNED` | `MISALIGNED`). Subject = the session log.

One way: run another agent over the persisted session log — prompts, thinking, tool use — against policies / guidelines.

If a session never saw a required document, that is this check. The log + `contextArtifacts` are the proof.

Example: `[objects_examples/agentic-session-alignment-evidence.json](./objects_examples/agentic-session-alignment-evidence.json)`.

### Deployment gates (policy-as-code)

The commit is not the last control point. Before software moves — merge, package publish, **promotion** — deployment gates evaluate the attached agentic process evidence (alongside the usual scans, build provenance, tests).

Typical gate: promote a package only if the coding sessions behind its commits pass policy-as-code.

Look up the process evidence on those commits, then the alignment evidence on their session logs, and verify:

- There is a human accountable (`owner`)
- Code was developed with human review (`reviewers`)
- Mandatory context was present in the sessions (`contextArtifacts` + logs)
- The agent stayed aligned with policies and task boundaries (alignment evidence, `intents`, `custom.requirements`)
- The agent did not attempt unapproved lateral operations
- Code was generated by an approved LLM
- The agent used approved MCP tools / harness
- Evidence exists and is signed

Fail → block the promotion (or route to a human). Pass → the package may move.

Same evidence, later choke point. The runtime tool does not gate. The server does.

## Artifacts

### Session log

`[objects_examples/agentic-session-log.json](./objects_examples/agentic-session-log.json)`

Captured by the runtime hook, persisted by the server. One per agentic session (incl. subagents).

- `sessionId` — this session
- `affectedEntities.gitCommit` — the commit this session contributed to (stamped on commit)
- `provider` — harness, agent, models (requested vs resolved)
- `parentSessionId` — when it is a subagent
- `timeline[]` — timeline events such as prompts, tool use, thinking tokens, can be captured via hooks.

### agentic-dev-process-evidence

`[objects_examples/agentic-dev-process-evidence.json](./objects_examples/agentic-dev-process-evidence.json)`

Signed, attached to the commit, queried by deployment gates.

- `predicateType`: `https://jfrog.com/evidence/agentic-dev-process/v1`
- `subject` = this git commit
- `sessionsLogs[]` = every uploaded log, uri + digest
- `owner` and `reviewers` = the human developer (same person)
- `result` = `COMPLETED` when the commit is ready for pre-merge review
- `contextArtifacts` = policies / guidelines that were injected (`policy`, `guideline`, …)
- `custom.requirements` = the task ticket
- `custom.baseCommit` = the base SHA
- `intents` / `processSummary` extracted from the sessions
- `createdBy` = the runtime tool

### agentic-session-alignment-evidence

`[objects_examples/agentic-session-alignment-evidence.json](./objects_examples/agentic-session-alignment-evidence.json)`

Optional. Produced on the server from the persisted session logs. Used by the gates. Does not replace process evidence — process evidence says what happened, this says whether it was ok.

- `predicateType`: `https://jfrog.com/evidence/agentic-session-alignment/v1`
- `subject` = the evaluated session log (uri + digest)
- `sessionsLogs[]` omitted — the subject already identifies the log
- `provider` = the alignment checker (harness / agent / models), not the coding agent
- `result` = `ALIGNED` | `MISALIGNED`
- `contextArtifacts` = policies / guidelines the session was checked against (`policy`, `guideline`, …)
- `custom.baseCommit` = the base SHA
- `custom.violations` = short violation list when `MISALIGNED`
- `owner` = who ran / owns the check
- `createdBy` = the alignment checker
